# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Luke Rebarchik's personal/professional site, live at https://lukerebarchik.com (custom domain on an Azure Static Web App): a single static page. There is no build step; npm is used for ESLint, the local dev server, the accessibility scan and copying the self-hosted fonts.

- **Lint:** `npm ci` once, then `npm run lint` (`npm run lint:fix` for autofixes). `eslint.config.mjs` lints the HTML markup with `@html-eslint` and the inline `<script>` blocks with `eslint-plugin-html` + `@eslint/js` recommended. Whitespace/layout rules are deliberately off to allow the compact hand formatting.
- **Preview locally:** `npm ci` once, then `npm run dev` and open http://localhost:4280. It runs the Azure Static Web Apps CLI (`swa start . --port 4280`, pinned to an exact version in `devDependencies`), which applies `staticwebapp.config.json`, so blocked paths return 404 locally too (but see the routing caveat below). Stop it with Ctrl+C.
- **Version fingerprint:** `index.html` carries `<meta name="build" content="lukerebarchik.com <hash> <commit> <date>">` in `<head>` and the same text as `<!-- build: … -->` before `</body>`. `<hash>` is 12 hex digits of SHA-256 over the page without those two lines (LF line endings), so it identifies the content. `npm run fingerprint` adds or updates it (commit `dev`, no date; run it after editing `index.html`, and it is idempotent). The deploy job runs the same script with `-- --commit <sha> --date <date>` before upload, then `-- --verify <url> --commit <sha>` against the deployed page (and https://lukerebarchik.com on `main`), so a deploy that did not go live fails. On PRs the commit is the merge commit GitHub builds, so it won't match the PR head SHA shown in the UI. The GitHub Pages mirror serves the committed `dev` stamp. Check any copy with `npm run fingerprint -- --verify <url>`, or `curl -s <url> | grep -o "<meta name=\"build\"[^>]*>"`. Code: `scripts/fingerprint.mjs`.
- **Browser tests:** `npm run test:a11y` (named for its first test) runs the Playwright suite in `tests/`: `a11y.spec.mjs` (`@playwright/test` 1.64.1 and `@axe-core/playwright` 4.14.0, exact-pinned) against WCAG 2.2 AA, and `gpc.spec.mjs` (Google Analytics must not load when the browser sends Global Privacy Control; its hit requests are aborted so tests never reach the real property), each at desktop and phone widths in light and dark mode. It runs `npm run fingerprint` first (so commit the stamped `index.html`). Without `BASE_URL` it reuses whatever already answers on port 4280, or starts `npm run dev`; either way `tests/global-setup.mjs` runs the fingerprint check (`verify()` in `scripts/fingerprint.mjs`) against the target and stops with an explanation if it isn't serving this checkout (for example another checkout's `npm run dev`). CI uses the same `npm run test:a11y`, so the preview, production and weekly scans also fail if the target doesn't match the commit being tested; set `BASE_URL=https://lukerebarchik.com` (or a preview URL) to scan a deployed copy. First run needs `npx playwright install chromium`. In CI, the `Accessibility scan` job scans every PR preview and production (its azurestaticapps.net hostname) after each deploy (not a required check; if a newer push redeploys before an older run's scan starts, the older run fails with "serves a different version", which only means it was superseded), and `.github/workflows/a11y-weekly.yml` scans production every Monday and opens or comments on a "Weekly accessibility scan failed" issue when the scan step fails (not for install or network failures). GitHub disables scheduled workflows after 60 days without repo activity; re-enable it in the Actions tab if that happens. Automated rules catch only part of WCAG; the manual review (#19) covers the rest.
- **Lighthouse:** `npm run lighthouse` (`scripts/lighthouse.mjs`, `lighthouse` 13.6.0 exact-pinned, using Playwright's Chromium) checks performance, best practices and SEO for `/` and `/privacy.html` on mobile and desktop, median of 3 runs, against the thresholds in `docs/decisions.md` D14 (mobile performance 85, desktop 95, best practices and SEO 100). Google Analytics is blocked in every run so it never sends hits; keep it that way. It targets `$BASE_URL` or https://lukerebarchik.com (`-- --base <url>` to override; add `--preview` for a PR preview, which Azure serves with `X-Robots-Tag: none`, so the `is-crawlable` audit is skipped there) and writes `lighthouse-results/` (gitignored). The `Lighthouse` CI job runs it after every PR preview and production deploy (not a required check), and `a11y-weekly.yml` runs it against production on Mondays and opens or comments on a "Weekly Lighthouse check failed" issue. A full run takes about 3 minutes; the first local run needs `npx playwright install chromium`, like the browser tests.
- **Deploy:** pushing to `main` deploys automatically via Azure Static Web Apps (`.github/workflows/azure-static-web-apps-ashy-water-0c11e7310.yml`, `app_location: "/"`). A `lint` job must pass before the deploy job runs. It always runs a secret scan of the history (`node .githooks/secure-git.mjs scan-history`). If every changed file is under `docs/` or ends in `.md` (docs-only), it skips `npm ci` and lint and the deploy job is skipped, so no preview environment is created. The `Lint` check still reports, and it is the required check on `main`. `skip_app_build: true` must stay set, or Azure's Oryx builder will detect `package.json` and try to npm-build the site. PRs against `main` get preview environments that are torn down on close. An earlier Azure workflow (`wonderful-dune`) failed and was removed; the `ashy-water` one is the live one.
- **Deploy token (not stored in GitHub):** the deploy and close jobs sign in to Azure with OIDC as the user-assigned managed identity `id-lukerebarchikcom-github-deploy` (resource group `lukerebarchikcom-github`), then fetch the token per run with `az staticwebapp secrets list` and mask it. The identity holds only the custom role `Static Web App Deploy Token Reader` (`Microsoft.Web/staticSites/listSecrets/action`), assigned on this one Static Web App. Its federated credentials trust `repo:luke80/lukerebarchik.com:ref:refs/heads/main` and `repo:luke80/lukerebarchik.com:pull_request` (PRs from forks get no OIDC token and can't deploy). The IDs are repository variables (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`), not secrets. To rotate the token, run `az staticwebapp secrets reset-api-key -n lukerebarchikcom-github -g lukerebarchikcom-github --subscription sub-lukerebarchik.com`; nothing in GitHub needs updating. In Git Bash, set `MSYS_NO_PATHCONV=1` before `az` commands that take a `/subscriptions/...` scope, or the path gets rewritten.
- **The whole repo root is uploaded to Azure,** so `staticwebapp.config.json` returns 404 for tooling files (`package*.json`, `eslint.config.mjs`, `playwright.config.mjs`, `swa-cli.config.json`, `_config.yml`, the config itself), the `scripts/` and `shots/` folders, test files and output (`tests/`, `test-results/`, `playwright-report/`, `blob-report/`, `lighthouse-results/`), all Markdown (`/*.md`, including `README.md` and `CLAUDE.md`), the project docs folder (`/docs*`, which also covers a bare `/docs`), every dot-path (`/.*`, which covers `.claude/`, `.github/`, `.env*`), and the `.gitignore` patterns. When adding a tooling file or a `.gitignore` entry, add a matching route. SWA wildcards only work at the end of a route or as an extension set (`/*.{log,pid}`); a wildcard after a dot inside a filename (`/npm-debug.log*`) silently fails to match. The first route (`/` → `/index.html`) must stay first: without it, production Azure 404s the homepage (one of the 404 patterns matches `/` there), even though the local emulator serves it fine. **The emulator is not a faithful test of routing.** Use `npm run dev` for a quick check, but before merging any route change, curl `/`, `/index.html` and the blocked paths on the PR's Azure preview environment (URL is printed as "Visit your site at:" in the Build and Deploy Job log, `gh run view <run> --job <job> --log`). The app is `lukerebarchikcom-github` in Azure subscription `sub-lukerebarchik.com`; production hostname is `ashy-water-0c11e7310.3.azurestaticapps.net`. After deploy, confirm with `curl -s -o /dev/null -w '%{http_code}' https://lukerebarchik.com/<path>`. The deploy action itself already drops `.git/` and `.github/`, but other dotfiles (e.g. `.gitignore`) do get uploaded.
- **GitHub Pages mirror:** Pages also publishes `main` (legacy Jekyll build) at https://luke80.github.io/lukerebarchik.com/ and ignores `staticwebapp.config.json`. `_config.yml` has a Jekyll `exclude` list that mirrors the Azure 404 routes. **Any route added to `staticwebapp.config.json` must also go in `_config.yml`**, and vice versa (`_config.yml` itself is 404'd on Azure). Pages only builds from `main`, so there is no preview: after merging, curl the excluded paths on the Pages URL.

## Before pushing or opening a PR

`main` is protected on GitHub: a PR is required, the `Lint` check must pass, and force-pushes and deletion are blocked. GitHub secret scanning and push protection are on, and so are Dependabot alerts and security updates (no `dependabot.yml`, so no routine version-update PRs). `.github/workflows/npm-audit.yml` runs `npm audit` every Monday (and on demand) and keeps one "npm audit: high or critical vulnerabilities" issue current; `scripts/audit-report.mjs` writes its description. Run it by hand with `gh workflow run npm-audit.yml`. `.github/workflows/uptime.yml` runs `scripts/uptime.mjs` daily against both sites (pages 200, a sample of blocked paths 404, every link, anchor and asset works; LinkedIn's 999 and 429 are accepted but its URL must match the expected profile) and keeps one "Uptime or link check failed" issue current the same way. Run it locally with `npm run uptime`. To test the alert, add a path that must return 200: `npm run uptime -- --expect-ok /no-such-page` locally, or `gh workflow run uptime.yml -f expect_ok=/no-such-page`. In Git Bash, set `MSYS_NO_PATHCONV=1` before either, or the `/path` is rewritten to a Windows path and rejected as a usage error. When you add a blocked route or change the LinkedIn URL, update the lists in the script. Locally, `.githooks/` (from `/secure-git`) refuses commits or pushes to `main` and anything that looks like a secret. Each new clone needs `/secure-git` once (or `git config core.hooksPath .githooks`) to wire it up. Work on a branch.

Run `npm run lint`, then invoke the `code-reviewer` subagent (`.claude/agents/code-reviewer.md`) on the pending changes. Resolve its blocking findings before `git push` or `gh pr create`.

## Structure

Each page is one self-contained file. The main one is `index.html`: all CSS is inline in a `<style>` block in `<head>`, and the only JavaScript is the Google Analytics (gtag `G-9QFZLHV9WK`) snippet, which adds the gtag script only when `navigator.globalPrivacyControl` is not set (#34; keep that check when touching the snippet), and two small inline scripts for the light/dark toggle (one in `<head>` applies the saved choice before paint, one at the end of `<body>` wires the button). Fonts (Archivo, IBM Plex Sans, IBM Plex Mono) are self-hosted in `fonts/` (Latin subsets, SIL OFL 1.1, licences alongside): `npm run fonts` (`scripts/fonts.mjs`) copies them from the exact-pinned Fontsource devDependencies, with the package version in each file name so `/fonts/*` can be served with a one-year immutable cache. After bumping a font package, rerun it and update the `@font-face` URLs and the preload in `index.html`. Don't add Google Fonts or other third-party requests back (privacy, #32). Keep it as one self-contained file unless asked otherwise. The one other page is `privacy.html` (#20), the privacy notice linked from both footers. Its `<style>` block starts with a verbatim copy of the subset of `index.html` rules it needs (fonts, colour tokens, base type, header, theme toggle, footer), and it has the same GA snippet and theme scripts. Rules it doesn't use (the Plex Sans 500 face, smooth scroll, the global heading sizes, `.btn.ghost`, `.lede`, reduced motion) are left out on purpose. When you change a shared rule in `index.html`, make the same change in `privacy.html`. The version fingerprint covers `index.html` only.

The files in `img/` (skylines, clouds, logo, profile photo, etc.) are leftovers from a previous version of the site and are **not referenced** by the current `index.html`.

## Design system conventions

The page uses the "Signal" style (see the comment at the top of the `<style>` block): white and charcoal, slate for secondary text, red as the single accent.

- **Color tokens** are CSS custom properties on `:root` (`--paper`, `--panel`, `--ink`, `--muted`, `--line`, `--rule`, `--accent`, `--accent-text`, `--cta`, `--cta-hover`, `--cta-ink`, `--band`, `--band-ink`, `--band-muted`, `--band-cta`, `--band-cta-hover`, `--band-cta-ink`, `--band-line`). `--accent` is for large type and marks only; small red text uses `--accent-text`, and buttons use `--cta`. The header button (`#theme`) toggles light and dark and saves the choice in `localStorage`. Dark mode redefines the same tokens twice: under `@media (prefers-color-scheme: dark)` guarded by `:root:not([data-theme="light"])`, and under `:root[data-theme="dark"]`. When changing or adding a color, update all three places. Use tokens (and `color-mix()` of tokens) rather than hard-coded colors. Body text, including `--muted`, needs 7:1 contrast on `--paper` and `--panel` in both themes; small labels need 4.5:1.
- **Type:** Archivo for headings (800 to 850 for `h1`/`h2`, lighter for `h3`, pull quotes and blockquotes; narrowed with `font-variation-settings:"wdth" …`), IBM Plex Sans for body text, IBM Plex Mono for the `.mono` class (the small uppercase label style). The font names are set directly; there are no type tokens.
- **Layout:** content is constrained by `.wrap`. Standard content sections use `<section class="block" id="…">`, opening with a `.head` grid: a `.mono` label column (section number and name) beside the `h2` and its `.sub` line. The header nav links `#work`, `#services`, `#experience` and `#hiring`.
- **Responsive:** each component's media query sits directly after its rules (breakpoints at 960/860/760/640/560px), collapsing grids to one column. CSS is written in a compact one-rule-per-line style; match it.

## Content

The page is effectively a résumé: hero (`#top`), three recent-project panels (`#work`), four services with prooflines (`#services`), the experience timeline (`#experience`), ways to hire (`#hiring`), recommendations (`#recommendations`), and the LinkedIn close (`#contact`): LinkedIn only, no email or form. Factual content (dates, titles, employers, figures like "$9.3M+" or "44M+") must stay consistent across the hero (including its figures and the "Since 1997" line), recent-work panels, services prooflines, the experience timeline, the `<meta name="description">` and `og:description`. When editing one, check the others.

## Privacy notice

`privacy.html` makes factual claims about Google Analytics: what it records, the 2-month cookie (`cookie_expires` in both GA snippets, checked by `tests/gpc.spec.mjs`), 2-month data retention, Google signals off, and Global Privacy Control. Keep it true. If GA settings, the GA snippet, hosting or third parties change, update the page and its "Last updated" date in the same PR. The facts were checked against Google's help pages on 2026-11-20 (links in #20).
